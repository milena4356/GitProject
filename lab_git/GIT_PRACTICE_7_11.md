# Практика Git: пункты 7–11 по схемам из методички

Рабочая ветка репозитория: `milena`. В GitHub основная ветка называется `main`, хотя в методичке она обозначена как `master`. Не меняй `main` напрямую без согласования: для пункта 7 создан PR `milena → main`.

## 7. Перенести изменения своей ветки на master

Сначала синхронизируй удалённые ссылки. В этом репозитории `master` соответствует `main`:

```bash
git fetch origin
git switch milena
git pull --ff-only origin milena
git rebase origin/main
```

Если возник конфликт: открой файл, оставь нужный итоговый вариант, затем:

```bash
git add <исправленный-файл>
git rebase --continue
```

Повторяй для следующих конфликтов. Для отмены всего rebase: `git rebase --abort`. После успешного rebase публикуй переписанную ветку только если это разрешено: `git push --force-with-lease origin milena`. Затем проверь PR: https://github.com/milena4356/GitProject/pull/1. Не сливай PR, если преподаватель не требует обновить основную ветку.

## 8. Передать итоговое состояние на сервер

```bash
git status
git log --oneline --graph --decorate --all
git push origin milena
```

## 9. Создать граф и преобразовать его в варианты a и b

Схема исходного задания: C1 → C2; от C2 идут две линии — C2 → C3 и C2 → C4 → C5. Указатель `master` стоит на C3, `test` — на C5.

Это упражнение нужно выполнять в отдельном учебном репозитории/ветке, не в основной истории проекта. Если граф уже создан по условию, перейди к нужному варианту ниже.

### Вариант a: объединить C3 и C5 в коммит C35

Поставь HEAD на ветку `test` (C5), затем слей `master` (C3) в неё:

```bash
git switch test
git merge --no-ff master -m "C35: merge C3 and C5"
```

Новый merge-коммит C35 должен иметь двух родителей: C5 и C3. После операции проверь `git log --oneline --graph --decorate --all`.

### Вариант b: линейная история C1 → C2 → C3 → C4' → C5'

Нужно переиграть C4 и C5 поверх C3, чтобы появились новые коммиты C4' и C5':

```bash
git rebase master test
```

Если возникнут конфликты, исправь файлы, выполни `git add <файл>`, затем `git rebase --continue`. После операции указатель `test` должен стоять на новом C5', а `master` — на C3.

### Бонус: конфликтуют ли C3 и C5?

Проверь оба сценария в отдельных копиях/ветках:
1. **Не конфликтуют:** C3 и C5 меняют разные файлы или непересекающиеся строки. Merge/rebase должен пройти без ручного разрешения.
2. **Конфликтуют:** C3 и C5 по-разному меняют одну и ту же строку. Git остановится и попросит разрешить конфликт.

После разрешения: исправь содержимое, `git add <файл>`, затем `git rebase --continue` (для rebase) или `git commit` (для merge). Не называй коммиты C3/C5 только по имени — конфликт определяется содержимым изменений.

## 10. Два изменения оформить одним коммитом

На одной из схем из пункта 9 внеси два произвольных изменения в файлы, затем объедини их в один коммит. Например, если изменения ещё не закоммичены:

```bash
# внеси оба изменения в рабочие файлы
git add <файл-1> <файл-2>
git commit -m "C: combine two changes"
```

Если преподаватель требует сначала создать два коммита, а затем объединить их, используй отдельную учебную ветку:

```bash
git add <файл-1>
git commit -m "change one"
git add <файл-2>
git commit -m "change two"
git rebase -i HEAD~2
```

Оставь первый как `pick`, второй пометь `squash` или `fixup`. Проверь результат через `git log --oneline`.

## 11. Перестроить граф с master, client и server

Целевая схема — линейная цепочка (от старых коммитов к новым):
`C1 → C2 → C5 → C6 → C8' → C9' → C3' → C4' → C10'`.
Указатели `master` и `client` стоят на C9', `server` — на C10'.

Имена со штрихом (C8', C9', C3', C4', C10') означают новые коммиты, созданные при переносе/переигрывании изменений; это не те же SHA, что у исходных C8, C9, C3, C4, C10. В графе, показанном в задании, исходные коммиты образуют две линии: C1–C2–C5–C6–C8–C9 (client/master) и C2–C3–C4–C10 (server), а C8 и C9 ещё не входят в основную верхнюю линию.

Для выполнения сначала создай граф с такими родительскими связями, как на рисунке, в отдельном учебном репозитории. Затем переиграй коммиты по порядку на нужную базу, используя `git rebase --onto <новая-база> <старая-база> <ветка>` или `git cherry-pick <SHA>`. Чтобы указатели совпали с целевой схемой, после успешного переноса поставь `master` и `client` на C9', а `server` — на C10'. Проверь результат:

```bash
git log --oneline --graph --decorate --all
git show-branch --all
```

Пункт 11 меняет саму топологию истории, поэтому не выполняй его на `main` или `milena` проекта: делай на временных ветках/в отдельном учебном репозитории.
