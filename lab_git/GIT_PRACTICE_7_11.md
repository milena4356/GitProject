# Практика Git: пункты 7–11

Рабочая ветка: `milena`. Основная ветка репозитория называется `main` (не `master`).

## 7. Перенос изменений своей ветки на основную

В удалённом репозитории подготовлена ветка `milena`. Для безопасного переноса на `main` создан запрос на слияние (Pull Request): это позволяет проверить diff перед изменением основной ветки. Фактическое локальное обновление и разрешение конфликтов выполняются в клоне:

```bash
git fetch origin
git switch milena
git pull --ff-only origin milena
git switch main
git pull --ff-only origin main
git switch milena
git rebase origin/main
# если есть конфликт: исправить файл, затем
git add <исправленный-файл>
git rebase --continue
# отмена при необходимости:
# git rebase --abort
git push --force-with-lease origin milena
```

Если преподаватель требует именно слияние, а не rebase, вместо rebase можно использовать `git merge origin/main`. Не выполняй оба варианта подряд. После проверки открой PR `milena → main` и слей его только если это требуется правилами сдачи.

## 8. Публикация конечного состояния

```bash
git status
git log --oneline --graph --decorate --all
git push origin milena
```

Проверь ветку и удалённый адрес перед push: `git branch --show-current` и `git remote -v`.

## 9. Перестроение истории коммитов

Схемы из исходного файла задания не извлеклись при чтении документа, поэтому ниже приведён воспроизводимый пример операций, а не утверждение, что он в точности совпадает с рисунком преподавателя. Делай упражнение только в отдельной ветке:

```bash
git switch milena
git switch -c practice/task-9
```

Пример исходного графа с двумя ветками:

```text
A---B---C1---C2  (practice/task-9)
     \\
      D---C3---C4  (practice/side)
```

Чтобы перенести коммиты на другую базу, используй `git rebase <новая-база>`; чтобы объединить две линии истории — `git merge <ветка>`. Сначала посмотри историю: `git log --oneline --graph --decorate --all`.

### Проверка конфликтов C3 и C5 (bonus)

- Если C3 и C5 изменяют разные файлы или разные строки, Git обычно применяет оба изменения автоматически.
- Если оба меняют одну и ту же строку несовместимым образом, при merge/rebase возможен конфликт; его нужно разрешить вручную.
- Конфликт зависит от содержимого изменений, а не только от названий коммитов.

## 10. Два изменения, объединённые в один коммит

В учебной ветке создай два независимых изменения и коммита, затем объедини их интерактивным rebase:

```bash
git switch -c practice/task-10 milena
# внеси изменение №1 и закоммить
git add <файл>
git commit -m "practice: change one"
# внеси изменение №2 и закоммить
git add <файл>
git commit -m "practice: change two"
git rebase -i HEAD~2
```

В редакторе оставь первый коммит как `pick`, а второй измени на `squash` (объединить с сообщением) или `fixup` (объединить без сообщения). Сохрани итоговое сообщение и проверь `git log --oneline`. Не переписывай опубликованную основную ветку.

## 11. Ещё одно преобразование графа

Для второго графа используй новую изолированную ветку и повтори требуемое преобразование из рисунка методички. Общая последовательность проверки:

```bash
git switch milena
git switch -c practice/task-11
git log --oneline --graph --decorate --all
# выполни нужный по рисунку rebase / merge / cherry-pick
git log --oneline --graph --decorate --all
```

Примеры:
- `git cherry-pick <SHA>` — перенести выбранный коммит на текущую ветку;
- `git rebase <ветка>` — переиграть коммиты текущей ветки поверх указанной базы;
- `git merge <ветка>` — объединить историю веток.

**Важно:** точную конечную топологию пункта 11 нельзя достоверно воспроизвести без самого рисунка. Сверь команды и ожидаемый граф с изображением в исходной методичке.
